| ---- | ---- | ---- | ---- | ---- |
| A | Single Agent | Gemini 2.5 Flash | 统一终端检查 | 2 |
| B | Multi-Agent | Gemini 2.5 Flash | 仅最终 Critic，检查失败才修订 | 2 |
| C | Multi-Agent | Gemini 2.5 Flash | Research、Strategy、Finance 角色级 Critic＋最终 Critic，检查失败才修订 | 2 |
| D | Multi-Agent | Granite 4.0 H Micro | 与 C 相同：角色级 Critic＋最终 Critic，检查失败才修订 | 2 |

四组执行相同的两个 case，每个 `case × condition` 正式执行一次，共 **8 个 planned runs：Gemini 6 次＋Granite 2 次**。预检与调试调用另计，不属于这 8 次正式实验。

由此分别衡量：

- B − A：Gemini 下 Single/Multi 的架构差异。
- C − B：增加角色级审查与条件修订的效果。
- C − D：相同优化 Multi-Agent 架构下 Gemini 与 Granite 的差异。

本轮取消固定修订对照和 Granite Single 组，不估计模型与架构的交互作用，也不比较固定修订与条件修订。B 仅在最终检查失败时修订；C/D 仅在相应角色或最终检查失败时修订，每处最多一次。

实验单位是 `case_id`，科学样本量为 **n = 2 cases**，结果定位为两案例工程验证。8 次计划运行不代表 8 个独立样本或保证 8 次成功；重复运行只能用于稳定性分析，不能增加独立样本量。

# 2. Tier 0：实验结果是否有效【v2.0 冻结要求】

Tier 0 使用以下四项检查：

* **同一实验输入**：同一完整商业 brief、冻结证据包和财务输入在 case 级归档；每个适用角色接收由同一确定性规则生成的角色视图。角色视图可以裁剪重复字段，但同一角色的可用事实集合不得按模型或可比条件改变。
* **同一语义协议**：A–D 使用同一 canonical 输出契约、轻量 JSON wire protocol、短证据 ID 映射、确定性展开和终端校验。Gemini 与 Granite 的 API 包装可不同；进入 provider 前的规范化 prompt、角色视图和 wire schema 必须保存 hash，C/D 的相同逻辑调用必须语义一致。
* **同一运行规则**：相同工具权限、32K context 上限、适用角色的输出上限、结构修复机会、语义修订机会和 60 分钟 run 硬限；角色提示词在正式运行前冻结。不同 tokenizer 的实际 token 数无需相等，但必须分别记录。
* **完整记录**：记录模型、配置、调用、超时、失败、确定性修复、结构 repair、语义 Revision、资源采样和全部中间 artifact；在每个 case 内随机安排条件运行顺序。

以下差异属于预设实验条件，不构成 Tier 0 违规：A 为 Single Agent；B 只有 final Critic；C/D 有 Research、Strategy、Finance 角色级 Critic 和 final Critic。只对 D 使用额外裁剪、额外容错或更宽终端门会使 C−D 失效。

# 4. Tier 2：可靠性、速度与资源指标【v2.0】

| 指标 | 预先固定的定义 | 处理规则 |
|---|---|---|
| **Completion rate** | 在 60 分钟共同硬限内完成该条件规定的全部角色、Critic/路由、统一终端检查并生成 canonical 输出的 runs / 全部 planned runs | 超时、API、Schema、模型和资源失败均保留在分母 |
| **MVP30 material rate** | 30 分钟内首次导出满足下述确定性 `MVP30` 契约的计划书材料的 runs / 全部 planned runs | 这是速度/产物可得性指标，不等于工作流完成或内容高质量，不恢复主观 Usable Draft Rate |
| **Time to first MVP30 material** | run 开始至首次形成 `MVP30` 材料；包含此前失败尝试和机械修复耗时 | 未达到者记 `not_reached`，不得把 1800 秒当成功时间 |
| **ValidPlan60 rate** | 60 分钟内生成通过统一 canonical 终端契约的完整计划并完成该条件规定流程的 runs / 全部 planned runs | 与 Completion rate 同时报告；若未来定义分离，必须新建规范版本 |
| **Time to first valid plan** | run 开始至完整计划首次通过统一终端契约；包含失败、repair 和 Revision 耗时 | 仅成功 run 有时间值；未完成不得进入成功耗时均值 |
| **Peak RAM / VRAM / pagefile** | 每个 run 的实测峰值与采样完整性 | 分项报告，不合成总分 |
| **Requests / tokens / retries** | 所有实际调用，包含失败、Critic、结构 repair 和语义 Revision | 按 provider、角色、目的和成功状态分项 |
| **Prompt / schema 负荷** | 每次调用的指令字符数、完整 prompt 字符数、provider 实际输入 tokens、wire schema UTF-8 字节数 | 用于检验加速机制是否真正减少隐性输入 |
| **阶段耗时** | prefill、generation、校验、确定性展开、Critic、Revision、导出及清理耗时 | 缺失采样与零耗时分开标记 |

`MVP30` 的确定性最低契约：13 个必需章节均存在且非空；Research 至少覆盖市场、客户和竞争/替代品三个主题；Strategy 给出定位、价值主张、商业模式、GTM 与防御性决策；Finance 的 21 行共同财务值由冻结输入和公式确定性生成；短证据 ID 可映射到冻结 packet；外部事实带证据 ID 或明确标为 assumption/unsupported；未知来源 ID、未知财务 ID、无法解析输出或缺失关键章节均不通过。30 分钟时可以尚未完成全部 Critic，因此 `MVP30` 不能写成完整工作流成功。

`ValidPlan60` 还要求完成条件 A/B/C/D 各自规定的 Critic 和条件修订路径、统一终端检查及 canonical 导出。低/中等级内容问题可以保留并进入 Tier 1 人工评分；结构不完整、未知引用、错误财务计算，以及模型声明为 factual 却没有合法证据 ID/evidence status 的 claim 属于自动硬失败。人工 Gold 核验后来判定“已有 ID 但语义上仍无充分支持”的高影响 claim 进入 Tier 1 指标，不追溯篡改自动完成状态。Critic 发现的 high/critical 问题、一次 Revision 后未再语义核验的问题必须原样留痕，不能因结构通过而宣称已解决。

# 5. Tier 3：Confidence 指标【需改】

**Claim grounding rate** = 有来源支撑的 claim / 总 claim

**Assumption transparency** = 正确标注为 assumption 的 claim / 实际无支撑的 claim

（**Assumption transparency**，衡量"诚实度"而非"正确性"；第二个指标很重要：它能捕捉一个大模型 vs SLM 的关键差异——SLM 可能不是编得更多，而是编了却不承认。这比单纯的事实精确率更贴合你的系统设计意图。）

# 6. 单个 Agent 的表现指标

本节用于诊断各角色的执行可靠性与资源消耗。最终内容的事实正确性、推理质量、商业合理性和表达质量，统一由 Tier 1 评价，不再为每个 Agent 的中间输出设置独立人工评分。

**6.1 核心指标：首次输出契约通过率**

$$
\text{首次输出契约通过率}
=
\frac{\text{首次提交即通过预设自动检查的逻辑任务数}}
{\text{已触发的逻辑任务总数}}
$$

“输出契约”指执行前固定、可以由程序明确判断的要求，例如：

* 通用检查：输出可解析、必需字段齐全、字段类型合法。
* Research / RAG：引用的 `source_id` 存在于冻结证据包中，来源符合 allowlist。
* Finance：按照预设公式与容差复算数值，检查结构化单位、币种和期间字段。
* Writer / Export：必需章节齐全、引用编号可以解析、导出结构符合要求。

这些检查合并为一次契约判定；失败时保留具体错误类型，不再为每个检查项单独建立主要指标。

计算规则：

* 一个逻辑任务及其重试视为同一个任务，重试不增加分母。
* 首次提交失败、超时或没有输出，均记为首次未通过；后续修复成功不能回改首次结果。
* 按工作流规则未触发的角色记为 `not_applicable`。
* 契约及检查规则在正式运行前固定，同一角色在可比条件下使用相同规则。

**该指标衡量可检查要求的符合程度。** 引用编号有效不代表来源支持论断；Critic 的输出格式合规也不代表其判断正确。不同角色承担不同任务，因此不能仅凭契约通过率进行能力排名。

**6.2 资源消耗：复用 Tier 2，按角色展示**

将 Tier 2 已记录的 **token 数、请求数和重试数**按 Agent 角色汇总，用于定位主要资源消耗和反复重试的位置。

统计包含失败尝试和修复调用，不只统计最终成功的调用。无需为角色重新建立资源评分，也不将资源消耗与质量合成为总分。

# 7. Multi-Agent 协作指标

协作是否改善最终结果，直接使用第 1 节已有的实验对照，并复用：

* Tier 1：Academic Quality Score、High-impact Unsupported Claim Rate。
* Tier 2：Completion rate、MVP30/ValidPlan60、两类首次产出时间、prompt/schema、token 与资源记录。

不再另设一套人工“协作质量评分”。本节仅保留以下两项自动过程诊断。

| 指标                            | 定义                                                                   | 用途                           |
| ------------------------------- | ---------------------------------------------------------------------- | ------------------------------ |
| **交接成功率**            | 在规定预算内完成的有效逻辑交接数 / 应执行的逻辑交接总数                | 判断上游产物是否正确交付给下游 |
| **调度与审查 token 占比** | Supervisor 与 Critic 模型调用消耗的 token / 全流程模型调用消耗的 token | 展示调度和审查占用的资源比例   |

**交接成功率的计算规则**

有效交接要求：指定下游收到正确的上游产物及版本，并且其执行所需的依赖已经满足。第 6 节检查产物自身是否符合契约，本指标检查产物之间的传递和依赖关系。

应执行的交接清单由预设工作流和分支规则确定，不能仅以日志中已经成功发生的交接作为分母：

* 应发生但因上游失败而未完成的交接，记为未成功。
* 按规则跳过的分支，不计入应执行交接。
* 每条逻辑交接计一次，重传不增加分母。
* 缺少必要日志时标记缺失，不能推定交接成功。

该指标检查结构化交接，不判断下游是否充分理解或利用了上游内容。

**调度与审查 token 占比的计算规则**

每次模型调用按照预先定义的职责唯一归类，包含其实际输入、输出及重试消耗。修订调用归入 Revision；交接文本已进入下游输入 token 时，不再额外增加一笔“handoff token”。

该比例只描述调度与审查的资源占用，不代表全部沟通成本，也不具有“越低越好”的单一方向。必须同时查看最终质量、完成率和总 token：更低的占比并不自动意味着更高的效率。

Single-Agent 条件的协作专属指标记为 `not_applicable`。预算上限、修订次数和终止规则是否得到遵守，复用 Tier 0 的规则检查与已有日志，不再增加协作评分。

# 8. 人工与自动评价的边界

人工评价集中于最终输出，不对每个 Agent 的中间输出另行评分。按最新决策，人工审核统一预留 1 小时，覆盖本轮可评分最终输出的评分与一次性 claim 核验；实际完成情况仍须记录。

| 评价内容                                      | 方式         | 人工具体负责什么                                          |
| --------------------------------------------- | ------------ | --------------------------------------------------------- |
| 六维 Academic Quality Score                   | 人工         | 按统一 rubric 对最终输出评分                              |
| High-impact Unsupported Claim Rate            | 人工＋自动化 | 判断 claim 是否属于高影响、是否得到充分支持；程序计算比例 |
| Claim grounding rate                          | 人工＋自动化 | 判断 claim 是否得到来源支持；程序计算比例                 |
| Assumption transparency                       | 人工＋自动化 | 判断无支撑 claim 是否正确标注为 assumption；程序计算比例  |
| 首次输出契约通过率、交接成功率                | 自动化       | 无逐项人工评分                                            |
| 完成率、token、请求、重试、内存及角色资源汇总 | 自动化       | 无逐项人工评分                                            |
| 调度与审查 token 占比                         | 自动化       | 无逐项人工评分                                            |
| 版本、输入一致性、路由、修订次数和预算检查    | 自动化       | 无逐项人工评分                                            |
| 第 9 节的统计计算                             | 自动化       | 无新增人工评分                                            |

**Claim 核验统一记录一次，供 Tier 1 和 Tier 3 共用。** 不为三个 claim 指标分别进行三轮审核，也不另做各 Agent 中间输出的 claim 审计。

MVP30 与首次生成有效计划所需时间均由程序记录，并严格限定为通过各自的自动契约；它们不代表商业逻辑或内容正确性。内容质量继续由 Tier 1 人工评价。

取消以下独立人工任务：是否可用判定、完整的问题严重性分级、Critic TP/FP/FN、Revision 修复与新增缺陷核验、人工编辑计时、成对偏好评分。高影响 claim 的识别继续保留，因为现有主要指标需要它。

LLM/Codex Judge 可以辅助提取待审核 claim，或用于可选的敏感性分析；其判断不能直接充当事实支持性或最终质量的真值。

# 9. 统计报告方式

独立分析单位为 `case_id`，科学样本量为 **n = 2 cases**。重复运行用于稳定性分析，不增加独立样本量，也不能替换失败的正式运行。

沿用第 1 节的预设比较，每项比较统一报告：

* 每个 case 的双方原始值及失败、缺失状态。
* 完整配对数量和逐 case 配对差值。
* **平均配对差值作为主要效应量**，中位数差值及差值的 IQR 作为补充。
* 改善、持平和恶化的 case 数，注明实际配对分母。

比例指标先在每个 case 内计算，再对适用 case 等权平均；保留各 case 的分子、分母及有效 case 数。

失败和缺失按以下方式处理：

* 没有可评分输出时，质量分记为缺失，不能填 0；同时报告全部计划运行的完成率。
* 未达到 MVP30 或未生成有效计划时，不将 1800/3600 秒硬限当作成功生成时间参与均值；两种状态分别标记 `not_reached`/`not_completed`。
* token、请求和重试等资源统计包含失败尝试的实际消耗。
* 分母为 0、运行失败和漏采集分别标记，不能混为同一种缺失。

**置信区间和显著性检验均为可选的探索性补充。** 如使用 Bootstrap，应以整个 case 为重采样单位，保留配对结构；如进行检验，应预先指定一种适用的配对检验，对同一检验族进行 Holm 校正，不根据结果挑选方法。

正文集中展示条件汇总表和配对比较表，逐 case 明细及过程诊断放入附表。结论首先限定于本次两个 case；不把“不显著”解释为等效或非劣。

# 10. 工程决策依据与候选阈值

工程决策复用 Tier 1–3 和第 6–7 节的结果，不新增中间输出人工标注。方案选择考虑最终质量、完成率与资源消耗；运行限制由自动日志检查。

| 决策                                   | 修订后的依据或候选规则                                                                                                                                                                                |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **是否保留角色 Critic** | 根据 C−B 在两个 case 上的质量差值、高影响无支撑 claim 率、完成率和额外资源消耗判断；报告改善、持平和恶化数量，不增设新的方向一致性门槛。该比较评价角色级审查与条件修订的组合效果。 |
| **条件修订是否正确执行** | B 的最终检查、C/D 的角色级及最终检查通过时跳过修订，失败时最多修订一次；检查路由、修订次数、预算与终止日志。本轮不设固定修订对照，不验证相对固定修订的质量非劣或 token 节省阈值。 |
| **是否接受 Confidence 改造**     | 根据 Claim grounding rate、Assumption transparency 的变化，以及高影响无支撑 claim 率判断。删除“过度保守率下降 ≥25%”，因为该指标已不在新版 Tier 3 中；不另设替代性的任意百分比门槛。                |
| **Granite 端到端是否可行** | 使用 A–D 共同紧凑协议：目标在 30 分钟内形成 MVP30 材料，完整 Multi-Agent 流程硬限 60 分钟；适用逻辑任务最多一次结构 repair、每个适用角色最多一次语义 Revision，并满足冻结内存上限。正式验收只使用实测结果。 |
| **如何报告模型差异** | 仅对 C/D 具有完整且可比结果的 case 报告 Gemini 与 Granite 的差异及有效配对数；本轮没有 Granite Single 组，不估计模型与架构的交互作用。 |
| **论文如何表达优势**             | 默认明确表述“在本次测试中质量更高”“token 消耗更少”等具体结果。预先设定最小实际差异，并不自动足以支持总体性的`outperforms`；表述范围应与证据相匹配。                                             |

Token、时间与完成率继续分别报告，但不将其解释为条件修订相对固定修订的收益。

每项比较应报告两个 case 的完整配对情况；缺少配对时须明确标注，同时报告失败，不能用剩余成功 case 代替完整比较。

删除依赖固定修订对照的 `3/100` 质量与 `15%` token 节省阈值；SLM 内存、共同 30/60 分钟时间门、结构 repair 和语义 Revision 限制在正式实验前固定。

# 11. 共同紧凑生成协议【2026-09-07 已批准】

## 11.1 保持不变的实验设计

* A/B/C/D、两个 case、8 个 planned runs、B−A/C−B/C−D、模型、32K context、角色集合与层级保持不变。
* C/D 均保留 Research、Strategy、Finance 角色级 Critic 和 Writer 后 final Critic；B 只保留 final Critic；A 保持 Single Agent。
* Tier 1 权重、全部决策关键 claim 的 Gold Ledger 分母、一次性人工核验和统计方法保持不变。
* 每个适用角色最多一次语义 Revision；Revision 后不增加第二轮语义 Critic。结构 repair 单独计数。

## 11.2 指令、wire schema 与 canonical 输出

* 每次调用的公共 system 指令与当前角色/任务指令合计不超过 **500 个 Unicode 字符**。冻结 brief、角色视图、证据片段、上游交接和 wire schema 不计入该 500 字符，但必须分别记录完整字符数与 tokens。
* 模型只生成无描述、少嵌套的轻量 JSON wire object；不使用 YAML。字段保持简短且可读，由确定性代码无损展开为既有 canonical Pydantic 契约。
* 同一逻辑调用的 C/D 使用相同规范化 prompt、角色视图、字段语义和 wire schema。Granite 不再接收完整重型 canonical schema；Gemini 适配器不得获得更宽的语义规则。两端统一执行同一严格本地校验。
* 当前“正文调用＋声明/grounding 调用”改为一次紧凑生成：正文同时携带冻结短证据 ID。代码根据预先冻结的映射补齐 `source_id`、chunk、quote/line、snapshot hash、claim lineage 和 canonical 字段；代码不得创造模型未选择的事实支持。

## 11.3 确定性角色视图与交接

* 完整 brief、证据包、上游 artifact 和所有原始响应继续不可变归档。
* 进入模型的角色视图由版本化确定性规则生成。下游交接只含当前角色必需的 claim ID、单句结论、claim type/status、短证据 ID、财务 ID、置信度候选和未解决问题；不得携带历史对话、旧修复文本或重复完整元数据。
* 不增加模型摘要 Agent。裁剪规则、证据路由和胶囊生成在 A–D 共同使用并保存 hash；任何 D-only 裁剪都会使 C−D 不可用。
* 短引用使用 `[E01]` 一类 case 内稳定 ID。每个业务角色仍对自己提出的事实选择证据；Writer 继承这些映射，不能重新发明或替换引用。

## 11.4 Critic、Revision 与可容忍错误

* Critic 保留固定指标和 0–4 分值，只返回紧凑评分向量、PASS/FAIL 状态，以及最多三个最高优先级问题。每个问题必须含 severity、criterion、受影响 claim/字段、证据 ID 和修复代码；禁止重写正文或输出长篇解释。
* Critic 的共同 gate 固定为 `revision_required = 存在 high/critical issue`、`blocking = 存在 critical issue`。0–10 换算分继续记录为诊断值，不单独触发 Revision。低/中等级问题保留在日志并进入最终人工质量评价，不强制触发整稿重写；失败门触发最多一次定向 Revision。
* Revision 只接收 Critic 指定的问题、相关字段和必要证据，并返回字段/claim patch；确定性代码应用 patch、验证 lineage 并保存前后差异。禁止重新生成整个角色 artifact。
* 允许的机械修复仅包括提取唯一完整 JSON object、删除 schema 外字段和冻结别名/枚举的无歧义归一化；每次修改保存 diff。代码不得补写论断、引用、数字或把 unsupported 改为 supported。
